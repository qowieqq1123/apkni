## 2. 二进制格式精确结论（来自反汇编，非猜测）

### 2.1 基础读写原语
源码反汇编位置：`NetBitStream` / `RawFile`（capstone 确认）

- `ReadByte`  = 1 个原始字节
- `ReadInt`   = 小端 `i32`（`BitConverter.ToInt32`，4 字节）
- `ReadString`= `u16 LE` 长度 `n`；`n==0` 返回空串且不消费终止符；
  否则读 `n` 字节 UTF-8，**再跳过 1 字节 `'\0'` 终止符**。
  - ⚠️ 修正点：文件末尾 `protos end\n` 之后**没有**终止符，
    因此 `ReadString` 在 EOF 处仅当字节确实存在且为 `0` 时才跳过——这是让解析器从
    `pos = size+1`（差 -1，FAIL）收敛到 `pos == size`（PASS）的关键修复。

### 2.2 `CreatePFunction` 布局（@0x105F440）
```
ReadInt  count
count × {
    ReadInt  funcId
    ReadInt  paramCount
    ReadString name
    paramCount × ProtocelParams（@0x105F644 起）{
        ReadByte type        ; 基础类型码（低字节有效）
        ReadByte subtype     ; 子类型/限定符
        ReadInt  count       ; 数组长度 / 计数
        ReadString name      ; 字段名
        ReadInt  typename_id ; 类型引用 id
        ReadInt  condition   ; 条件标志（≠0 表示带跳过分支）
        if condition != 0 {
            ReadInt index
            ReadInt n
            n × ReadInt args ; 条件分支参数
        }
    }
}
```

### 2.3 顶层结构（CreateNetWorkProtocolInfo @0x105C898，反汇编确认）
```
ReadString -> "protos begin\n"      ; 实际带前导换行: "\nprotos begin\n"
ReadString -> "netstruct\n"
CreatePFunction (count=0, 空表)       ; 占位
CreatePFunction (count=1066) -> 结构定义表  ; PFunction == 一个结构体
ReadString -> "proto\n"
ReadInt    -> protocel 数量 N
N × CreateProtocel {
    ReadInt key
    CreatePFunction 表A
    CreatePFunction 表B
}
ReadString -> "protos end\n"
```

### 3.1 类型码观察（节选自 `selectRoleStruct`，id=10001）
字段：`id 0x07` / `name 0x0a` / `sex 0x02` / `icon 0x06` / `level 0x04` …
- `type=0x0a` 对应字符串字段（与 `ReadString` 一致）。
- `type=0x12`（即十进制 18 / 数组，低字节 `0x12` 视作容器）配合 `subtype=0` 且 `typename_id≠0` 时，
  表示该字段是「元素结构引用」数组，引用目标即 `typename_id` 对应的结构体（私服建表的关键）。

### 3.2 protocel 示例（key=43）
```
==== protocel key=43 ====
  [table A] 6 entries : 43_2(1) 43_3(3) 43_4(4) 43_5(3) 43_6(2) 43_7(1)
  [table B] 7 entries : 43_1(8) 43_2(1) 43_3(1) 43_4(2) 43_5(1) 43_6(2) 43_7(1)
```
每个 `key_funcid` 即「消息号」，`table A` 通常对应 C→S，`table B` 对应 S→C（具体方向需结合 Lua 调用确认）。

### 3.3 Lua `do_protocol_*` 交叉核对结果

运行：`python -X utf8 tools/lua_crosscheck.py --binary out/binary --protocels out/protocels.csv -o out`

| 指标 | 数值 |
|------|------|
| 协议表总映射数 | 2,519 条（56 个 protocel key） |
| Lua 引用到的 (key, funcId) | 290 个 |
| 两者重叠 | 288 条 |
| Lua 独有（协议表缺失） | **2 条** |
| 协议表独有（Lua 未引用） | **2,231 条** |

#### 结论
- 绝大多数协议消息由 **C#（Unity）端** 处理，Lua 仅处理 UI/展示层协议。
- 完全被 Lua 覆盖的 protocel key：**key=12**、**key=22**（100%）。
- Lua 覆盖率较高的活跃系统：
  - `key=26` (93%)、`key=19` 灵兽 (83%)、`key=0` 玩家基础 (67%)、`key=16` 古宝 (61%)、`key=7` (43%)
- 大量 key（如 35、37、247-255 等）Lua 覆盖率为 0%，完全由 C# 处理。

## 6. 关键假设与限制

- 解析**严格遵循反汇编语义**，未做启发式容错；因此 `pos==size` 与四段标签匹配即视为格式完全正确。
- 标签字符串带前导 `\n` 是文件真实内容（非解析误差）。
- `type`/`subtype` 的具体枚举含义（除 `0x0a=字符串`、`0x12=结构数组` 外）尚未逐一定名，
  需结合 `dump.cs` 的字段类型推断补全。
- 当前未改动任何游戏文件，仅做离线逆向与文档产出。
